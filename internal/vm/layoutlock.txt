# The layout lock's targets: where package vm's hot code and the Go
# runtime's hot data must be in a build of internal/cmd/v8bench, for each
# configuration. See internal/cmd/layoutpad, which reads this file and
# writes the pads (go generate ./internal/vm), and docs/optimizing.md.
#
#   anchor LEVER TARGET [@ADDR] SYMBOL
#
# puts SYMBOL at TARGET modulo 4,096 (code) or 64 (data, the levers DH, DW
# and DG) by the lever's pad. ADDR, a code anchor's, is its address as the
# layout was last recorded, which every build must keep on its page, ADDR
# over 4,096: a pad that grows past what the code before its anchor shrank
# moves the anchor and everything after it a page, every offset modulo
# 4,096 the same, which the targets alone cannot see (E did at c7c7830a,
# and json_stringify_decimals was 46% slower at every placement). The
# regeneration and TestLayoutLock fail then, naming the first anchor that
# moved, its pad and the anchor before it: move what grew in that pad's
# range out of it, after its anchor, as b5df63ea did; where the move is
# meant -- code that grew by a page or more -- layoutpad -pages records
# the new addresses. The targets are the layout at db306c0e, before
# the slowdowns of the rounds after it; W's, regCallW's, now rhCallW,, the layout at
# 679d54b3. Q anchors the register interpreter's loop, runReg, and W the
# call path after it; its handlers follow (reg_table*.go). X is the one
# lever outside package vm: a pad at the start of internal/regexp, linked
# before vm, which anchors the matcher's run (and with it its search and
# the searches for a unit) at bef551a1's layout; internal/bytecode's growth
# had moved it 3,520 bytes and made the V8 suite's RegExp 3.5% slower.
# H is the assembly pad before the native handlers' block (nativeEnter,
# nativeCallH, the feedback handlers, regNativeHandlers), which package
# vm's assembly puts after every closure of its named functions: it
# anchors regNativeHandlers at fba9570a's layout: the closures one round
# added moved it 672 bytes (608 in one of its branches, which made
# Octane's RegExp and the generator tests slower). E and C hold the
# built-ins' hot loops between A and D, which the placements do not vary:
# E anchors firstElem (builtins.go), C asciiCaseMemo (casetables.go),
# at f9829c9f's layout; the files the renames after it put among them had moved them
# 2 KB and made array_indexOf 23%, json_round_trip 10% and string_upper
# 7% slower at every placement. E's pad is kept short of a page:
# Function.prototype's key reservation (8b5d6339) took it from 32 stores
# to none, three keyOrder calls (c7c7830a) took firstElem 96 bytes past
# that, the pad went to 4,011 bytes, and everything after it moved 4 KB
# against the code before it and the packages linked before vm -- its
# offsets modulo 4 KB the same -- and json_stringify_decimals was 39%,
# json_stringify_records 15% and json_stringify_indent 11% slower at
# every placement than with E short. The reservation is in keyorder.go, after T, and E 20
# stores. R and S, after W, hold a replace's loop
# (regExpReplaceIn, regexp_abstract.go) and the string builder
# (partsBuilder, string.go) at f9829c9f's layout, which the files the
# renames put before them had moved: regexp_replace_dollar was 4 to 8%
# slower at every placement, where the base, its code shifted by 32 to
# 96 bytes, was not. I, F, L, N, P and U hold, at 3ecb8200's layout,
# code the renames and the positions after them moved: I the BigInts'

# forward_construct was 18%, generator_next 14%, bigint64_divmod 13%,
# bigint256_arith 9% and string_upper 8% slower at 2f05d3fc. P, the pad

# VT, VA, PR and SH, and the assembly pads HJ and HT, are positions the lock's rule

# functions more than 8 KB past their range's anchor at 1d08a62d --
# jitHostCall 251 KB past J, the JIT's leaf stubs (jitLeafFast,
# jitGoFast) 485 KB past Z, the array methods' callbacks 140 KB past JP
# -- each anchored where its pad, at its least, left it; P holds regCall
# with the JIT too. GK and MVT hold two groups of generics, the string
# appends (strAppend) and the regular expression leaves
# ((*regexpLeaf).match), where layoutpad -show -all -generics found a
# generic pad landing right before them.
#
# The wasm and jit+wasm configurations are v8bench built with the
# quickjs_wasm tag (and quickjs_jit), which links the WebAssembly engine
# and installs its namespace in every runtime (internal/cmd/v8bench's
# wasm.go), as qjs does. Their code anchors are the targets of the
# configuration without the engine, so that vm's hot code is where it is
# there: such a build links the functions only the bridge reaches, which
# moved vm's code against itself, and json_stringify_unicode with the
# JIT was 50 ns where it was 37 without the engine. The runtime moves
# around vm there, and two data targets cannot be reached: a 16-byte
# variable more lies before writeBarrier (Windows: x/sys/windows's
# canDoSearchSystem32Once), so that writeBarrier and gcController move
# together, and the wasm configurations have writeBarrier at 0x020 where
# it is at 0x010 without the engine -- 16 bytes off, the nearest place
# that keeps gcController at its target. jit+wasm has both of its jit
# configuration's.
